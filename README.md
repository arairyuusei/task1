# キーマンレター: 人事情報ページのURL特定

企業のHPだけを入力に、人事情報が載っている以下のページのURLを特定します。
**このプログラムの成果物はURLまで**です。個別記事（例:「2026.08.31 人事異動の
お知らせ」）の特定と人事情報の抽出は、ここで得た一覧URLを入力とする後段の
プログラムが担当します。

| カテゴリ | 内容 | 更新検知の方式 |
|---|---|---|
| `company_profile` | 会社概要／企業概要／会社案内 | 本文ハッシュ |
| `officers` | 役員一覧／役員紹介／経営体制 | 本文ハッシュ |
| `news_public` | 一般向けニュース一覧（ニュースルーム等） | 記事一覧に新着があるか |
| `news_ir` | IR向けニュース一覧（IRニュース／適時開示） | 記事一覧に新着があるか |

住友林業（sfc.jp）での期待される出力は次の4件です。実サイトの構造を確認して
ルールを組んでいます。

```
company_profile  https://sfc.jp/information/company/aboutus/
officers         https://sfc.jp/information/company/officer/
news_public      https://sfc.jp/information/newsroom/
news_ir          https://sfc.jp/information/ir/news/
```

`news_public` はグローバルナビ上の「ニュースルーム」（タブ）を採ります。
その配下に全件一覧「ニュースリリース」(`/information/news/`) がありますが、
監視対象としてはナビから直接辿れるタブのほうが安定するためです。

## ファイル

```
keyman_finder.py   本体（クロール／スコアリング／検証／更新検知／CLI）
rules.py           キーワード辞書。判定の調整はまずここだけを触る
llm_adjudicate.py  曖昧ケースのLLM判定＋後段の抽出プロンプト雛形
test_offline.py    住友林業の構造を模した架空サイトでのオフラインテスト
```

```bash
pip install requests beautifulsoup4 lxml
python test_offline.py                                  # 動作確認（通信なし）
python keyman_finder.py discover https://sfc.jp/ --company 住友林業 --out out/sfc.json -v
python keyman_finder.py check out/sfc.json              # 更新検知（差分のみ出力）
python keyman_finder.py batch companies.csv --out-dir out/   # company,url のCSV
```

## 処理の流れ

```
トップページ取得
  ↓ ① グローバルナビ・フッタから全リンク＋アンカーテキストを収集（深さ0）
  ↓ ② 「会社情報」「IR」「ニュース」「サイトマップ」ハブを2件ずつだけ取得して
  ↓    1階層掘る（深さ1）… 役員一覧はトップに無く会社情報の下にあるため必須
  ↓ ③ robots.txt の Sitemap 宣言と /sitemap.xml を読み、pathパターンに
  ↓    当たるURLだけ候補に追加（深さ2、JS描画サイトの保険）
  ↓ ④ 候補をカテゴリ別にスコアリング（アンカー・URL・掲載位置・階層）
  ↓ ⑤ 上位候補だけ実際に取得し、ページ内容で検証（役職語が並ぶか／
  ↓    設立・資本金の項目があるか／日付付きリンクが並ぶか）
  ↓ ⑥ 確信度が低いカテゴリのみ LLM に候補一覧を渡して選ばせる（任意）
  ↓ ⑦ 更新検知用の指紋（ETag／本文ハッシュ／既知記事URL）を保存
JSON出力
```

1社あたりの取得回数は20回前後（テストでは19回）に収まります。

### スコアリングの考え方

アンカーテキストとURLのキーワード一致を主軸に、次を加減点します。

- グローバルナビ内にある `+3` … 正規のページはナビに載る
- アンカーが12字以内 `+2` … ラベル的なリンクである証拠
- 階層が浅い `+2 / +1`、同一URLが3回以上出現 `+1`
- 会社情報ハブ配下で見つかった `+3`（`officers`, `company_profile`）
- 英語版・アーカイブ・PDF・個別記事URL・ページ送りは減点

誤検知しやすいものは `rules.py` の `negative` で明示的に落としています。
役員報酬ページ、グループ会社役員一覧、採用サイトの経営者メッセージ、
個別記事URL（`/news/2026/08/...`）などです。

同じURLが複数の文言でリンクされることがあります（「ニュースルーム」と
「ニュースルーム一覧へ」など）。文言ごとに採点して最良を採るので、
`^会社概要$` のような完全一致パターンが取りこぼされません。

ニュース系カテゴリでは、首位と12点以内の候補のうち「トップページの
グローバルナビにあり、パスが浅いもの」を優先します（`prefer_nav_tab`）。
タブとその配下の全件一覧はスコアが近接するため、この後処理で決めています。

### 内容検証

URLだけでは判断を誤るため、採択前に中身を見ます。

- `officers`: 役職語（代表取締役・執行役員・監査役…）が4種以上かつ計8回以上
- `company_profile`: 商号・設立・資本金・従業員数・事業内容などの項目が4つ以上
- `newslist`: 日付付きリンクが4件以上

検証を通れば `confirmed`、スコアは足りるが検証未通過なら `likely`、
それ以下は `uncertain` として `needs_review` に入り、人手確認またはLLM判定へ回します。

ニュース一覧がJavaScriptで描画されているサイト（住友林業がこれに該当します）では、
静的HTMLに記事が入っていません。この場合、記事が取れないことは「一覧ページでない」
証拠にはならないので減点せず、`evidence.render = "javascript"` を立てて
`needs_rendering` に入れます。URLの特定はできているので `needs_review` には入れません。
`<link rel="canonical">` を見て正規URLに寄せるので、旧サイトの重複ページ
（例: `/japanese/corporate/officer.html`）が選ばれにくくなっています。

### LLMの使いどころ

ルールベースで決着しなかったカテゴリだけ、候補URLとアンカーテキストという
小さな構造化データを渡して選ばせます（`--llm`）。HTML全文を投げないので安価で、
候補外のURLを返した場合は破棄するのでハルシネーションも入りません。
`llm_adjudicate.py` の `EXTRACTION_PROMPT` は、後段で会社概要・役員一覧ページから
人事情報を抽出する際のプロンプト雛形です（参考用）。

## 更新検知

`discover` の出力JSONがそのまま状態ファイルになります。`check` は
`If-None-Match` / `If-Modified-Since` 付きで再取得し、304なら何もしません。

- 会社概要・役員一覧: ナビやフッタを除いた本文のハッシュ比較。変化があれば
  `content_changed` を発行し、`page_url` を後段に渡す。
- ニュースタブ: 記事URLの集合を比較し、新着があれば `new_entries` を発行して
  `list_url`（=タブのURL）を後段に渡す。どの記事が人事案件かの判定はしません。
- タブがJS描画で記事一覧を持たない場合は、トップページの新着ブロックを
  指紋の代わりに使います（`entry_source` に実際に見ているURLが入る）。
  日本企業のサイトは「トップに最新5〜10件を静的に出し、全件一覧はJSで描く」
  構成が多いため、この代替経路だけで更新検知が成立します。
  住友林業の場合、2026.08.31「人事異動のお知らせ」はトップページから
  静的HTMLで取得できます。ただし掲載は数件どまりなので、
  取りこぼしを避けるには1日1回以上の頻度で `check` を回す必要があります。

出力例:

```json
{"events": [
  {"category": "news_public", "type": "new_entries",
   "list_url": "https://sfc.jp/information/newsroom/", "new_count": 1,
   "new_entries": [{"date": "2026-09-01", "title": "役員人事および組織改編について",
                    "url": "https://sfc.jp/information/newsroom/2026/0901_01.html"}]},
  {"category": "officers", "type": "content_changed",
   "page_url": "https://sfc.jp/information/company/officer/"}
]}
```

一覧の解析（`extract_news_entries`）は2つの目的にしか使っていません。
そのURLが本当に一覧ページかの検証（日付付きリンクが4件以上あるか）と、
新着の有無の検知です。記事タイトルのキーワード判定は持たせていないので、
「人事異動」「代表取締役の異動」「組織改編」といった表現ゆれへの対応は
後段プログラム側に一本化されます。

`<link rel="alternate" type="application/rss+xml">` があれば `feeds` に入ります。
毎日全社をポーリングするより、RSSがある企業はRSSを見るほうが軽くなります。

## うまくいかないケースと対策

| ケース | 症状 | 対策 |
|---|---|---|
| JavaScript でナビを描画 | トップからリンクが取れない | sitemap.xml で救う。それでも駄目なら Playwright でレンダリングして同じ `extract_links` に渡す |
| JavaScript で記事一覧を描画 | 一覧URLは分かるが記事が取れない | `needs_rendering` に入る。トップページの新着ブロックで代替するか、一覧を生成しているJSON APIを企業ごとに1回調べて直接叩く |
| 役員一覧がPDFのみ | `officers` が `not_found` | PDFも候補に含め（`negative` のPDF減点を緩める）、後段でPDFテキスト抽出 |
| 人事異動がIRの適時開示PDFのみ | 一覧に日付付きリンクが並ばず検証に落ちる | `news_ir` の代替として `IRライブラリ`／`適時開示`ページを `alternates` から採用 |
| ニュースが別ドメイン（PR TIMES等） | 同一ドメイン制約で除外 | `same_site` に許可ドメインリストを追加 |
| 持株会社と事業会社でサイトが別 | 役員が別ページ | 入力を企業単位ではなく法人単位にし、グループ会社一覧から子会社サイトを辿る |
| IR代行ベンダーの共通CMS | URLが `/ir/` 配下で統一 | 実はこれは有利。ベンダー別のパターンを `rules.py` に足すと精度が上がる |
| 旧サイトが残存 | 古い役員名を拾う | canonical と検証で大半は防げる。加えてページ内の「◯年◯月◯日現在」を拾って古いものを警告する運用を推奨 |

## 運用上の注意

- `robots.txt` を既定で尊重し、同一ホストへのアクセスは既定1.5秒間隔、
  1社あたり60リクエストが上限です。`--ignore-robots` は原則使わないでください。
- `--user-agent` に連絡先を入れてください（既定値はダミーです）。
- 収集した役員名は個人情報です。公開情報のみを扱うとしても、利用目的の明示と
  訂正・削除の受付窓口を用意してください（サイトの利用規約で自動収集を
  禁じている企業もあるため、対象リストの精査も必要です）。
- `registrable_domain` は主要な `.co.jp` 系サフィックスのみのため、
  本番では `tldextract` に置き換えてください。

## 精度を上げる進め方

1. 主要50〜100社の正解URLを手作業で作り `eval_set.csv` にする
   （`company,url,category,expected_url`）。
2. `batch` の `summary.csv` と突き合わせてカテゴリ別の正解率を出す。
3. 外した事例だけを見て `rules.py` の重みかパターンを1つ足す。
   コードは触らない。
4. `needs_review` の件数を監視する。ここが人手確認キューになります。

ニュースタブに「人事・組織」などのカテゴリ絞り込みリンクがある企業では、
そのURL（例: `?category=jinji`）を `news_public` の代わりに採用したほうが
後段の負荷が下がります。必要になったら `rules.py` にカテゴリ絞り込み用の
パターンを足して候補に含める形で拡張できます。

補足として、上場企業であれば EDINET（有価証券報告書）や適時開示で役員情報を
突き合わせられます。HPの更新漏れ・反映遅れの検出に有効ですが、本プログラムは
「企業HPのみ」という前提を守るため対象外にしています。
